Deep dives

Partitioning sensor_version_state to stop an ACU blow-up

PI-7372

Cut a 39M-row / 47GB table down to 1.6M / 7.7GB and made every query touch one partition instead of sixteen.

Signal sensor_version_state had grown to ~39M rows / 47GB, and every per-sensor query scanned the whole table. In staging and prod that showed up as Aurora ACU pressure and slow batch-eval writes. The table needed to shrink and change how it was written — an index alone wouldn't fix it.

I audited the writes first: workers wrote a state row for every evaluation, but only triggered rows are ever read anywhere in the codebase — non-triggered writes were ~93% of volume for zero downstream use. The fix had two parts that had to land in order: (1) partition the table by HASH(sensor_id) so per-sensor reads and bulk expiry/turn-off updates prune to one partition instead of scanning all sixteen, and (2) stop writing non-triggered rows so the lean table stays lean. Since it was a live-data cutover, the migration carried its own drift guard that aborts the swap rather than risk corrupting the table.

Jun 4 · dev-validated
Shipped the partition migration and query changes #1002

16-way HASH(sensor_id) partition, composite primary key, cloned indexes/FKs, a drift guard, and the five call sites updated to filter by sensor_id so they prune. Merged behind a hold — dev-rehearsed only, prod cutover deferred to its own runbook.

early Jun · cutover attempt #1
A full-table copy blew the 300s Lambda timeout

The one-time INSERT … SELECT to populate the partitioned twin timed out inside the prod migration Lambda's 300s cap (run #836); a manual multi-hour retry still didn't finish. Copying all 39M rows was never going to fit the window.

Jun 9
Root cause → copy only the triggered rows #1011

Because non-triggered rows have no reader, the copy only needs the ~1.3M triggered rows (~3% of the table). One filter clause turned a copy that couldn't finish into one that fits the 300s window comfortably. Paired with #1008 so new non-triggered writes don't undo the shrink.

Jun 9 · same day
Cutover #2 — the drift guard caught a type mismatch #1014

Prod declared five key columns as unbounded varchar; my twin had created them as varchar(255). The drift guard did its job — aborted the swap instead of silently truncating, rolled back cleanly, left prod untouched. I recreated the columns unbounded and added a metadata-only widening pass for any stale twin.

Jun 8–9 · coordinated cutover
Stopped the leak going forward #1008

Cutover order: pause the batch-eval workers and the expiry Lambda → run the filtered migration → verify row counts → flip SENSOR_STATE_TRIGGERED_ONLY=true so workers skip non-triggered upserts and hard-delete on turn-off/expiry → resume workers only once the flag is confirmed live, so nothing refills the fresh table.

A query-plan regression on the claim path

actions-processor

Found a claim query running at ~217,000 cost where the right index-scan plan costs ~19 — by reading its EXPLAIN output, not guessing.

Signal Batches were getting stuck in a "fetching" state after ECS scaled workers down mid-claim. Separately, weeks later, a staging incident showed the action-claim query degrading badly under backlog.

I fixed the scale-down bug first (#935, May 6): batches claimed by a worker that got scaled away never released, so nothing else could pick them up. The bigger story came later. Rather than guess at the slow query, I pulled its plan directly — the OR-based claim clause forced a sequential scan plus sort at ~217,000 cost, while a pending-only query against the right partial index cost ~19. That's a gap no amount of code review catches without actually running EXPLAIN.

Jun 26 · hotfix
Split the claim query around the plan gap #1053 → #1055

claimNextActions split into a pending-first query (hits idx_triggered_actions_pending) with a rare stale-in-flight fallback on its own partial index. #1053 carried an unrelated dependency, so I closed it and shipped #1055 — a hotfix-only cut without the coupling — to get the fix out fast.

Jun 29
A stale migration bundle blocked the next deploy #1056

Staging's knex_migrations already recorded #1055's migration from the incident hotfix, so Knex's validateMigrationList hard-failed with "the migration directory is corrupt" and blocked all pending migrations. #1056 added a reconciliation step to prune stale rows before migrating, plus a gate requiring staging to migrate before prod could be approved.

Jul 1–2 · course-correct
Reverted the over-strict fix, shipped the durable one #1063 (closes #1062)

#1056 had two problems in practice: its reconciliation only self-heals idempotent migrations (most of this repo's aren't), and its new gate also hard-failed on skipped runs — the normal case for engine-only commits — which blocked its own deploy. #1063 reverted the reconcile code, softened the gate to fail only on an actual migration failure, and replaced the code-level net with a policy: no out-of-band migrations, and any DB hotfix ships its migration file in the same PR.

Result: the claim query now runs an index scan instead of a 217k-cost sequential scan under backlog — and, just as important, my own over-correction to the deploy gate got caught in practice and replaced with a narrower fix plus a documented policy, instead of quietly causing its own outages.

A deploy-gate suite — with Datadog picking what to test

sensors-api-test-suite

Built a stage→prod deploy gate, let 90 days of Datadog traffic rank the 15 endpoints worth gating, and deleted a redundant ~720-line home-grown monitor.

Signal sensors-api had no synthetic coverage between a stage deploy and a prod deploy — a regression could reach production with only manual QA in the way. The real question wasn't "add tests," it was which of ~45 endpoints were worth gating on, and whether Datadog already solved part of the problem.

First, Datadog had to actually see individual endpoints. #965 (May 14) found APM was only recording HTTP-method names — GET, POST — because dd-trace was configured at the infra layer but never loaded in the process. Importing the tracer as the very first line of app.ts, ahead of Express/pg/http, let auto-instrumentation record the real route (GET /api/sensors/:sensorId). That one change unlocked everything below.

With per-endpoint data, I ranked endpoints by 90 days of production traffic (Feb 26 – May 26) rather than by what looked important. That flipped one real scope call: agentsRoutes.ts was excluded from the original 45-endpoint plan, but the data showed it carried 4 of the top 5 business endpoints by volume — so it moved in-scope, and the target narrowed from a blind 45 to a focused, traffic-ranked 15.

May 15
First synthetic suite #968

22 endpoints wired into a Bruno collection with a prod-safe.txt allowlist restricting prod runs to read-only GETs, run on a schedule and after every deploy.

May 26 · scope pivot mid-PR
Cut a ~720-line home-grown monitor before it shipped #982

The original plan was a scheduled heartbeat with an SSM auto-pause kill switch, CloudWatch alarm, IAM split, and tiered Slack alerts — ~720 lines of workflow + ~360 of Terraform. Two review passes converged on the same finding: Datadog's APM, health checks, and synthetics already covered prod monitoring end-to-end into PagerDuty, so the canary re-solved a solved problem while adding attack surface (a kill switch nothing armed). I deleted it wholesale — net -1,027 lines — and replaced it with a deploy-gate model: the stage run blocks every prod deploy on failure; the prod run is advisory; a 2h/6h cron is a Slack-only backup behind Datadog, not a replacement for it.

Jun 1
Diagnosed a false "API contract broken" page #997

The gate paged on-call as a contract violation, but the six failing endpoints all returned healthy 200s — only schema validation failed, with a bare expecting ';'. Running the pinned @usebruno/cli@3.3.0 directly showed the cause: Bruno's sandboxed require() has no JSON loader, so require("./x.json") evaluates the file as JavaScript and chokes on the first "key":. I emitted schemas as .js modules, added a lint guard against regressing to .json, and split tooling errors from contract breaks so a tooling bug can't page on-call as a contract failure again.

Org & tenancy access hardening

PI-6651 → PI-7873 / 7901 / 7920

Closed org-scoping gaps route by route across read and write paths — and caught the one regression the staged rollout produced the same day.

Signal A security audit surfaced org-scoping gaps across sensors-api routes: some trusted a client-supplied org_id without verifying membership, and org-id comparisons weren't case-normalized.

I closed this route-family by route-family rather than as one flag flip — over-restricting a legitimate M2M caller was as real a risk as leaving a gap open. #1076 made org-id comparisons case-insensitive at both the gate and row-access layers. #1077 and #1084 extended flag-independent org scoping to the remaining read endpoints, so a user-token caller is scoped to their real memberships even while enforcement is off — with a fail-closed 403 if scope can't be resolved. #1020 documented enforcement across all eleven M2M-scoped routes.

Jul 13 · staged rollout, regression found
Enforcement in staging broke 5 wildcard-permitted routes

Once ORG_ACCESS_ENFORCEMENT_ENABLED was staged for a real flip, M2M clients on the 12 routes marked allowWildcards: true — cache warmers, the agents service, cross-org reads — started getting rejected with MISSING_ORG_ID. Root cause: requireOrgAccess.ts wasn't distinguishing "no org_id supplied" from "org_id required and absent" on routes that had opted into wildcards.

Jul 13
Scoped fix, not a rollback #1089

The fix only changes behavior on routes that already had allowWildcards: true — all reads, none create/update/delete. M2M callers keep their unrestricted scope; user-token callers narrow to their own accessibleOrgIds, covered by new spec cases for both. Strict routes are untouched and still 400 on a missing org_id. Staging's enforcement flag (#1088) went ahead only after this landed.

Result: org-scoping closed across read and write paths with case-insensitive comparisons and documented M2M contracts — and because I watched the staged rollout rather than fire-and-forgetting it, the one regression got caught, root-caused, and fixed same-day instead of reaching prod.

Feature & API work

Product-facing sensors-api features: transactional handlers, audit history, dependency-derived sources, cascading PATCH updates, and DRAFT-state promotion. One worth calling out is #1026: prod test failures showed GET/POST /api/agents/sensor_analysis returning a 503 at ~30s. The cause was an API Gateway 30s integration timeout racing an unbounded Trino COUNT(*) that had a 120s app budget — the app had headroom the edge didn't. I bounded the request to 21s with abort propagation, returned total: null when the count can't finish rather than 503ing the whole response, and cached the windowed count for 300s to keep the deploy-gate path warm.
