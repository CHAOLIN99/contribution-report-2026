Overview

Four investigations account for the bulk of this window's work. A hot-table partitioning project (PI-7372) stopped a runaway Postgres table from driving Aurora ACU pressure in staging and prod. A parallel reliability thread on the same claim-path table diagnosed and fixed a query-plan regression using EXPLAIN output rather than guesswork. A from-scratch deploy-gate testing suite replaced a proposed home-grown monitoring stack after a Datadog audit showed the monitoring already existed — and that same Datadog audit picked which 15 of ~45 sensors-api endpoints were worth testing at all. And a months-long org/tenancy access-control hardening effort closed scoping gaps route by route, catching and fixing a production regression of its own along the way.

Each is written up below as signal → diagnosis → what shipped → result, with every PR referenced inline at the point it mattered. The remaining, smaller initiatives keep the original table format further down.

Deep dives

The four threads that drove most of this window's design, investigation, and cross-repo coordination.

Stopping the ACU blow-up: partitioning sensor_version_state

PI-7372
Signal sensor_version_state had grown to ~39M rows / 47GB and every per-sensor query scanned the whole table. In staging and prod this showed up as Aurora ACU pressure and slow batch-eval writes — the table needed to shrink and the write pattern needed to change, not just get an index.

The first pass at root cause was a row audit: workers were writing a state row for every sensor evaluation, triggered or not, but only triggered rows had a reader anywhere in the codebase — non-triggered writes were ~93% of write volume for zero downstream consumption. The plan had two parts that had to land in a specific order: (1) partition the existing table by HASH(sensor_id) so per-sensor reads and the bulk expiry/turn-off updates prune to one partition instead of scanning all sixteen, and (2) stop writing non-triggered rows going forward so the lean table stays lean. Both required a live-data cutover with zero tolerance for silently corrupting sensor_version_state, so the migration carried its own schema drift-guard that aborts the swap rather than risk it.

Jun 4 · dev-validated
Ship the partition migration and query changes #1002

HASH(sensor_id) 16-way partition, composite primary key, indexes/FKs cloned from the live table, an information_schema drift guard, and the five call sites (onConflict targets, bulk expiry/turn-off queries) updated to filter by sensor_id so they prune. Merged behind a hold: dev-rehearsed only, production cutover deliberately deferred to its own runbook.

early Jun · cutover attempt #1
Full-table copy blows the 300s Lambda timeout

The one-time INSERT … SELECT to populate the partitioned twin timed out inside the prod db-migration Lambda's 300-second cap (run #836), and a manual multi-hour retry outside the Lambda still didn't finish. Copying all 39M rows was never going to fit the deploy window.

Jun 9
Root cause → filter the copy to triggered rows only #1011

Since non-triggered rows have no reader, the one-time copy only needs the ~1.3M triggered rows (~3% of the table), not all 39M. One filter clause turned a copy that couldn't finish into one that comfortably fits the 300s window. Paired with #1008 below so new non-triggered writes don't undo the shrink immediately after cutover.

Jun 9 · same day
Cutover attempt #2 — drift guard catches a type mismatch #1014

Prod declares five key columns (sensor_version_state_id, execution_id, etc.) as unbounded varchar; the migration's twin had created them as varchar(255). The drift guard did its job — it aborted the swap instead of silently truncating data, rolled the transaction back cleanly, and left prod untouched. Fixed by creating the twin's columns unbounded and adding a metadata-only widening pass for any environment with a stale varchar(255) twin already in place.

Jun 8–9 · coordinated cutover
Stop the leak going forward #1008

Cutover sequence: pause the batch-eval workers and the expiry-cleanup Lambda → run the filtered migration → verify the partitioned table and row counts → flip SENSOR_STATE_TRIGGERED_ONLY=true in staging and prod tfvars, which makes workers skip non-triggered upserts, hard-delete on turn-off/expiry, and emit batch.states_not_triggered_skipped to Datadog → resume workers only once the flag is confirmed live, so nothing writes non-triggered rows back into the fresh table before the flag takes effect.

Triggered-actions claim path: same table family, a query-plan regression

actions-processor
Signal Batches were getting stuck in a "fetching" state after ECS scaled workers down mid-claim, and — separately, a few weeks later — a staging incident showed the action-claim query degrading badly under backlog.

The scale-down issue (#935, May 6) was fixed first: batches claimed by a worker that got scaled away before finishing never released, so nothing else could pick them up. The bigger diagnostic story came later, when a staging incident made claimNextActions itself the suspect. Rather than guess at a fix, the query's plan was pulled directly: the existing OR-based claim clause forced a sequential scan plus sort with an estimated cost around 217,000, while a pending-only query against the right partial index cost roughly 19. That's the kind of gap no amount of code review catches without actually running EXPLAIN.

Jun 26 · hotfix
Split the claim query around the plan gap #1053 → #1055

claimNextActions split into a pending-first query (hits idx_triggered_actions_pending) with a rare stale-in-flight fallback on its own partial index. #1053 carried an unrelated PI-5940 dependency and was closed in favor of #1055, a hotfix-only cut of the same fix shipped without that coupling — a deliberate call to get the query-plan fix out fast without waiting on a larger, riskier PR.

Jun 29
A stale migration bundle blocks the next deploy #1056

#1052's merge commit predated #1055's migration file, but staging's knex_migrations table already had that migration recorded from the incident hotfix — so Knex's validateMigrationList hard-failed with "the migration directory is corrupt" and blocked the entire deploy, including unrelated pending migrations. #1056 shipped a reconciliation step to prune stale rows before migrating, plus a harder gate requiring the staging migration to succeed before prod could be approved.

Jul 1–2 · course-correct
Revert the over-strict fix, ship the durable one #1063 (closes #1062)

Two problems surfaced with #1056 in practice: the reconciliation logic only safely self-heals idempotent migrations, and most of this repo's migrations aren't idempotent — pruning a row for a non-idempotent one and having its file reappear later would make up() error instead of no-op. And the new gate's hard-fail also fired on skipped runs (the normal case for engine-only commits), which blocked #1056's own deploy. #1063 reverted the reconcile Lambda code back to pre-#1056, softened the gate to only hard-fail on an actual migration failure, and replaced the code-level safety net with an operational one: a README policy that out-of-band migrations are never allowed, and any incident hotfix touching the DB ships its migration file in the same PR.

Result: the claim query now runs on an index-scan plan instead of a 217k-cost sequential scan under backlog; and — just as important — an over-correction to the deploy gate got caught in practice and replaced with a narrower fix plus a documented policy, instead of being left in place to cause its own outages.

Designing the deploy-gate suite: letting Datadog pick what to test

sensors-api-test-suite
Signal sensors-api had no synthetic coverage between a stage deploy and a prod deploy — a regression could reach production with nothing but manual QA in the way. The open question wasn't just "add tests," it was which of ~45 endpoints were worth gating on, and whether Datadog already solved part of this problem.

Before endpoint selection could be data-driven, Datadog had to actually see individual endpoints. #965 (May 14) found that APM was only ever recording HTTP-method-level resource names — GET, POST — because dd-trace was configured at the infra layer (sidecar, env vars) but never actually loaded in the sensors-api process. Importing the tracer as the very first statement in app.ts, ahead of Express/pg/http, let Express's auto-instrumentation populate resource.name with the real route template (GET /api/sensors/:sensorId). That one change is what made a per-endpoint Datadog view — and everything that follows below — possible.

With that in place, a Datadog dashboard built against 90 days of production traffic (Feb 26 – May 26) was used to rank endpoints by actual usage rather than by what looked important. The traffic breakdown was the deciding input on at least one real scope call: agentsRoutes.ts had been excluded from the original 45-endpoint route-inventory plan, but the Datadog data showed it carried 4 of the top 5 non-health business endpoints by volume — so it moved from excluded to in-scope, and the target surface narrowed from a blind 45 down to a focused, traffic-ranked 15.

May 15
First synthetic suite, route-inventory scope #968

22 endpoints wired into a Bruno collection with a prod-safe.txt allowlist restricting prod runs to read-only GETs, run on a schedule and after every deploy.

May 26 · scope pivot mid-PR
Cut a ~720-line home-grown monitoring stack before it shipped #982

The original plan for this PR was a scheduled heartbeat with an SSM-backed auto-pause kill switch: a CloudWatch alarm on 3 consecutive failures triggering a Lambda that flips an SSM parameter, principal-level IAM split so only the trigger Lambda could arm it, tiered Slack alerting — roughly 720 lines of workflow plus 360 lines of Terraform plus a runbook. Two parallel review passes (a director-tech-code-review pass and a duty-engineer-reviewer on-call-lens pass) converged on the same finding: Datadog's APM, ECS/ALB health checks, and synthetics were already covering continuous prod monitoring end-to-end into PagerDuty, and the home-grown canary was solving an already-solved problem while adding new attack surface of its own (a kill switch nothing was arming). The auto-pause subsystem was deleted wholesale — net -1,027 lines — and replaced with a deploy-gate model: the stage Bruno run blocks every prod deploy job on failure; the prod run after deploy is advisory (Slack + a GitHub Actions annotation, no auto-rollback); a cron run every 2h (prod) / 6h (stage) is a Slack-only backup sitting behind Datadog → PagerDuty, not a replacement for it.

Jun 1
Diagnose a false "API contract broken" page #997

The gate went red and paged on-call via Slack → Datadog → PagerDuty as a contract violation, but the six failing endpoints were all returning healthy 200s — only the schema-validation step failed, with a bare expecting ';' syntax error. Running the pinned @usebruno/cli@3.3.0 directly (not reading docs about it) showed the actual cause: Bruno's sandboxed require() has no JSON loader, so require("./schemas/x.json") reads the file and evaluates it as JavaScript, and a schema's first "key": blows up on the colon. Fixed by emitting schemas as .js modules instead of .json, added a lint guard so no .bru file can regress to requiring a .json schema again, and split validator/loader errors into their own category so a tooling bug can't masquerade as a contract break in front of on-call again.

Org & tenancy access hardening

PI-6651 → PI-7873 / 7901 / 7920
Signal A security audit surfaced org-scoping gaps across sensors-api read/write routes: some routes trusted client-supplied org_id without verifying membership, and org-id comparisons weren't case-normalized.

The closure work moved route-family by route-family rather than as one flag flip, because the risk of over-restricting a legitimate M2M caller was as real as the risk of leaving a gap open. #1076 (Jul 6) fixed org-id comparisons to be case-insensitive at both the gate and row-access layers. #1077 and #1084 extended flag-independent org scoping to the remaining read endpoints — agents, sensors, collections, evaluations, and action-assets — so a user-token caller is scoped to their real memberships even while the enforcement flag is off in an environment, with a fail-closed 403 if scope can't be resolved. #1020 documented enforcement across all eleven M2M-scoped routes so the contract is explicit rather than implicit.

Jul 13 · staged rollout, regression found
Flipping enforcement in staging breaks 5 wildcard-permitted routes

Once ORG_ACCESS_ENFORCEMENT_ENABLED was staged for a real flip, M2M clients calling the 12 routes marked allowWildcards: true — cache warmers, the agents service, cross-org read paths that were designed to accept a missing or wildcard org_id — started getting rejected with MISSING_ORG_ID. Root-caused to requireOrgAccess.ts: the gate wasn't distinguishing "no org_id supplied" from "org_id required and absent" on routes that had opted into wildcards.

Jul 13
Scoped fix, not a rollback #1089

Rather than widen access broadly, the fix only changes behavior on routes that already had allowWildcards: true before this PR — all twelve are reads, none create/update/delete. M2M callers on those routes still resolve to the same unrestricted scope they always had; user-token callers narrow to their own accessibleOrgIds, never unrestricted, covered by new spec cases for both caller types. Strict routes are untouched and still 400 on a missing org_id. Staging's enforcement flag (#1088) went ahead only after this landed.

Result: org-scoping closed across read and write paths with case-insensitive comparisons and documented M2M contracts, and — because the staged rollout was watched rather than fire-and-forgotten — the one regression it produced was caught, root-caused, and fixed same-day instead of reaching prod.
